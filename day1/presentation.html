1الدرس 1 · Futures و async/awaitDart

الـ Future «وعد» بقيمة ستصل لاحقاً — وهو أساس Riverpod

  • Dart تعمل على خيط واحد (Single Thread) مع حلقة أحداث (Event Loop)، لذلك الانتظار لا يجمّد الشاشة بل يسمح للـ UI بالرسم أثناء الانتظار.
  • FutureProvider و AsyncNotifier و AsyncValue كلها مبنية على Future — لهذا نبدأ به.
  • الطريقة القديمة: then / catchError / whenComplete — الحديثة: async / await مع try / catch / finally، والكود يُقرأ كأنه متزامن.
  • رمي خطأ داخل دالة async يحوّله تلقائياً إلى Future فاشل، وon تلتقط نوع خطأ محدد.
💡 في التطبيق: كل زر في الشاشة ينفّذ مثالاً ويكتب النتيجة في «الكونسول» أسفل الشاشة.
Future<String> fetchUserName(int id) async {
  await Future.delayed(const Duration(milliseconds: 500));
  if (id <= 0) {
    throw ArgumentError('رقم المستخدم غير صالح: $id');
  }
  return 'مستخدم رقم $id';
}

// 2) الطريقة الحديثة: async / await مع try / catch / finally
Future<void> _awaitStyle() async {
  try {
    final name = await fetchUserName(-5); // سيفشل عمداً
    _log(name);
  } on ArgumentError catch (e) {
    _log('خطأ متوقع: ${e.message}');
  } finally {
    _log('finally تعمل دائماً');
  }
}

تسلسلي مقابل متوازي — من أهم نقاط الأداء

  • تسلسلي: الطلب الثاني لا يبدأ إلا بعد انتهاء الأول.
  • Future.wait: كل الطلبات تبدأ معاً — عيبه: النتيجة List<Object>.
  • Records (Dart 3): (f1, f2).wait — الأنواع محفوظة لكل عنصر ✅
تسلسلي: await ثم await≈ 1200ms
متوازي: Future.wait أو Record.wait≈ 700ms
// تسلسلي: الطلب الثاني لا يبدأ إلا بعد انتهاء الأول ≈ 1200ms
final a = await fetchUserName(1);
final b = await fetchOrdersCount();
_log('تسلسلي: $a / $b طلب ← ${sw.elapsedMilliseconds}ms');

// متوازي باستخدام Future.wait: كل الطلبات تبدأ معاً ≈ 700ms
final results =
    await Future.wait([fetchUserName(2), fetchOrdersCount()]);
_log('Future.wait: $results ← ${sw.elapsedMilliseconds}ms');

// متوازي باستخدام Records (Dart 3): الأنواع محفوظة لكل عنصر ✅
final (name, count) =
    await (fetchUserName(3), fetchOrdersCount()).wait;
_log('Record.wait: $name / $count ← ${sw.elapsedMilliseconds}ms');

timeout · Future.any · Completer

  • timeout: إذا لم تنتهِ العملية خلال المهلة نرمي TimeoutException.
  • Future.any: نأخذ أول نتيجة تصل (مثلاً من عدة خوادم).
  • Completer: تحويل كود يعتمد على callbacks (مكتبة قديمة) إلى Future.
⚠️ تنبيه: بعد أي await قد يكون المستخدم خرج من الشاشة — لذلك نتحقق من mounted قبل setState.
try {
  await fetchUserName(1).timeout(const Duration(milliseconds: 200));
} on TimeoutException {
  _log('انتهت المهلة! الخادم بطيء');
}

// Future.any: نأخذ أول نتيجة تصل (مثلاً من عدة خوادم)
final fastest = await Future.any([
  Future.delayed(const Duration(milliseconds: 300), () => 'الخادم A'),
  Future.delayed(const Duration(milliseconds: 100), () => 'الخادم B'),
]);

// 5) Completer: تحويل كود يعتمد على callbacks إلى Future
Future<String> _legacyApiAsFuture() {
  final completer = Completer<String>();
  Timer(const Duration(milliseconds: 300), () {
    completer.complete('نتيجة من API قديم');
  });
  return completer.future; // نعيد الـ Future فوراً، ويكتمل لاحقاً
}

Provider و Notifier: «الوصفة» والحالة القابلة للتغيير

  • Provider بسيط: قيمة للقراءة فقط.
  • Notifier: حالة قابلة للتغيير + الدوال التي تغيّرها. build() تعيد القيمة الابتدائية.
  • نغيّر الحالة بإسناد قيمة جديدة لـ state ← كل من يراقب يُعاد بناؤه.
  • بدون ProviderScope في أعلى الشجرة يظهر خطأ عند أول ref.watch.
// Provider بسيط: قيمة للقراءة فقط
final greetingProvider =
    Provider<String>((ref) => 'أهلاً بك في Riverpod 👋');

// Notifier: حالة قابلة للتغيير + الدوال التي تغيّرها
class CounterNotifier extends Notifier<int> {
  // build() تعيد القيمة الابتدائية
  @override
  int build() => 0;

  // نغيّر الحالة بإسناد قيمة جديدة لـ state ← كل من يراقب يُعاد بناؤه
  void increment() => state++;
  void decrement() => state--;
  void reset() => state = 0;
}

final counterProvider = NotifierProvider<CounterNotifier, int>(
  CounterNotifier.new,
);

NotifierProvider للسلة + Provider مشتق للإجمالي

final taxRateProvider = Provider<double>((ref) => 0.15);

// Provider يعتمد على providers أخرى: يُعاد حسابه تلقائياً عند تغيّرها
final cartTotalProvider = Provider<double>((ref) {
  final items = ref.watch(cartProvider);
  final tax = ref.watch(taxRateProvider);
  final subtotal = items.fold<double>(0, (sum, item) => sum + item.price);
  return subtotal * (1 + tax);
});

class CartNotifier extends Notifier<List<CartItem>> {
  @override
  List<CartItem> build() => [];

  // ⚠️ الحالة immutable: لا نعدّل القائمة (state.add) بل ننشئ قائمة جديدة
  void add(CartItem item) => state = [...state, item];
  void removeAt(int index) => state = [...state]..removeAt(index);
}
⚠️ الفخ الأشهر: state.add(item) يعدّل نفس القائمة فلا يعرف Riverpod أن الحالة تغيّرت — أنشئ قائمة جديدة دائماً.

AsyncNotifierProvider و StreamProvider

  • build هنا async: Riverpod يعرض loading تلقائياً حتى تنتهي.
  • AsyncValue.guard: ينفّذ ويلتقط الخطأ ويحوّله إلى AsyncError تلقائياً.
  • StreamProvider — ساعة حية: Stream.periodic(1s) ← Riverpod يلغي الاشتراك تلقائياً عند عدم الحاجة.
  • clock.value: آخر قيمة أو null أثناء التحميل.
class TodosNotifier extends AsyncNotifier<List<String>> {
  // build هنا async: Riverpod يعرض loading تلقائياً حتى تنتهي
  @override
  Future<List<String>> build() async {
    await Future.delayed(const Duration(seconds: 1)); // محاكاة طلب شبكة
    return ['مراجعة Futures', 'تجربة Streams'];
  }

  Future<void> add(String title) async {
    final current = state.value ?? [];
    // AsyncValue.guard: يلتقط الخطأ ويحوّله إلى AsyncError تلقائياً
    state = await AsyncValue.guard(() async {
      await Future.delayed(const Duration(milliseconds: 400)); // POST
      return [...current, title];
    });
  }
}

@riverpod class و keepAlive

  • class ← يولّد NotifierProvider؛ نرث من _$Likes (مولّد) بدل Notifier<int>.
  • @Riverpod(keepAlive: true) ← لا يُحذف من الذاكرة حتى لو لم يستخدمه أحد. مناسب للإعدادات وبيانات المستخدم الحالي.
  • الاستخدام مطابق تماماً للـ providers اليدوية: ref.watch(likesProvider)

6الدرس 6 · family و autoDisposeRiverpod

باراميتر لكل حالة + تنظيف تلقائي + كاش مؤقت

// FutureProvider.autoDispose.family<النوع, الباراميتر>
final productProvider = FutureProvider.autoDispose.family<Product, int>(
  (ref, id) async {
    debugPrint('🟢 إنشاء productProvider($id)');
    // onDispose: تنظيف (إلغاء طلبات، إغلاق streams...)
    ref.onDispose(() => debugPrint('🔴 حذف productProvider($id)'));

    await Future.delayed(const Duration(milliseconds: 800)); // GET /products/$id

    // keepAlive: نمنع الحذف مؤقتاً = كاش لمدة 10 ثوانٍ
    final link = ref.keepAlive();
    final timer = Timer(const Duration(seconds: 10), link.close);
    ref.onDispose(timer.cancel);

    return (id: id, name: 'منتج رقم $id', price: id * 25.0);
  },
);
// نمرّر الباراميتر كأننا نستدعي دالة
final product = ref.watch(productProvider(id));

ماذا يحدث للحالة عند الخروج من الشاشة؟

  • family ← كل قيمة باراميتر لها حالة مستقلة ومخزّنة منفصلة: productProvider(3) ≠ productProvider(4)
  • autoDispose ← حذف الحالة من الذاكرة عندما لا يستخدمها أي Widget (مثلاً عند الخروج من شاشة التفاصيل).
  • keepAlive ← إذا رجع المستخدم خلال 10 ثوانٍ تظهر البيانات فوراً بدون تحميل.
  • Notifier مع family: الباراميتر يصل عبر الـ constructor (أسلوب Riverpod 3) — NotifierProvider.autoDispose.family

8الدرس 8 · OverridesRiverpod

«استبدل هذا الـ provider داخل هذا النطاق»

  • 1) الاختبارات: نستبدل الـ Repository الحقيقي بـ Fake.
  • 2) البيئات: تنفيذ مختلف للتطوير والإنتاج (انظر تعليق main.dart).
  • 3) النطاق المحلي: ProviderScope متداخل يعطي قيمة مختلفة لجزء من الشجرة.
overrideWithValue(v)قيمة جاهزة overrideWith((ref) => …)دالة إنشاء جديدة
📌 لماذا override لـ temperatureProvider أيضاً؟ لأنه يقرأ الـ Repository، فيُنشأ من جديد داخل هذا النطاق ويرى الـ Fake.
// تنفيذ وهمي (Fake) — نفس الواجهة، نتيجة ثابتة وفورية
class FakeWeatherRepository implements WeatherRepository {
  @override
  Future<int> temperature(String city) async => 99;
}

// ProviderScope متداخل: نستبدل الـ Repository لهذا الجزء فقط
ProviderScope(
  overrides: [
    weatherRepositoryProvider.overrideWithValue(
      FakeWeatherRepository(),
    ),
    temperatureProvider.overrideWith(
      (ref, city) =>
          ref.watch(weatherRepositoryProvider).temperature(city),
    ),
  ],
  child: const CityTemperatureTile(city: 'الرياض'),
),

override لكل عنصر في القائمة + override في الاختبارات

  • Provider «بدون قيمة»: throw UnimplementedError(...) — يجب أن يُعطى قيمة عبر override وإلا يرمي خطأ.
  • داخل القائمة: لكل عنصر ProviderScope خاص مع overrideWithValue(city) — لاحظ: لا نمرّر city للـ constructor.
  • في الاختبار: ProviderContainer = نفس ProviderScope لكن بدون Widgets، و .test يتخلّص من الحاوية تلقائياً بعد انتهاء الاختبار.
  • .future ننتظر النتيجة النهائية للـ FutureProvider.
test('temperatureProvider يستخدم الـ Repository الوهمي', () async {
  // ProviderContainer = نفس ProviderScope لكن بدون Widgets
  final container = ProviderContainer.test(
    overrides: [
      weatherRepositoryProvider.overrideWithValue(
        FakeWeatherRepository(),
      ),
    ],
  );

  // .future ننتظر النتيجة النهائية للـ FutureProvider
  final temp =
      await container.read(temperatureProvider('الرياض').future);

  expect(temp, 99); // النتيجة من الـ Fake وليس من الـ API ✅
});

ملخص اليوم الأول — درس واحد لكل سطر

الدروس 1 – 4

  • 1 · Futures: وعد بقيمة لاحقاً — await للقراءة، Future.wait / (a, b).wait للتوازي، microtasks قبل events، والـ Future يُنشأ مرة واحدة لا داخل build.
  • 2 · الأساسيات: ProviderScope في الأعلى، Providers كمتغيرات global، watch في build · read في الأحداث · listen للتأثيرات الجانبية.
  • 3 · الأنواع: Provider · NotifierProvider · AsyncNotifierProvider · FutureProvider · StreamProvider — والحالة immutable دائماً.
  • 4 · توليد الكود: @riverpod صياغة واحدة، autoDispose افتراضياً، keepAlive لما يعيش طوال التطبيق.

الدروس 5 – 8

  • 5 · AsyncValue: switch أو when — بدون isLoading يدوي، refresh للسحب و invalidate لإعادة المحاولة.
  • 6 · family / autoDispose: حالة لكل باراميتر، تنظيف تلقائي عند الخروج، ref.keepAlive() + Timer = كاش مؤقت.
  • 7 · حقن الاعتماديات: واجهة + Provider + ref.watch — الشاشة لا تعرف شيئاً عن API أو Dio.
  • 8 · Overrides: Fake في الاختبارات، ProviderScope متداخل، ProviderContainer.test.
